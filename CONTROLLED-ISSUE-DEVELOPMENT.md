# Controlled issue and customer acknowledgement — isolated development

This is an additive development continuation of `7ee2b4d`. Production, `main`, the live site and the existing isolated hosted project are untouched. No additional hosted test users are required. Original draft PDF/Word downloads, auth, team-sync queue/conflict rules and the four original Academy lessons remain available.

## Delivered

- `sql/controlled-issue-isolated.sql` extends the existing isolated schema. It requires an explicit session acknowledgement, runs transactionally, refuses reapplication, and is never loaded by the app. Existing members default to `editor`. `viewer` reads; `editor` edits; `approver` and `admin` also issue/invite/revoke. Roles are provisioned by the test-project owner through SQL, not by client claims. Membership remains workspace-wide; direct table access and internal write-function access are denied.
- Controlled issue freezes the current synchronised service/PAT/lighting version after an authorised approver records scope and limitations. Duplicate/stale issues fail. SHA-256 binds the exact canonical JSON document, site snapshot, source version and approval scope. Corrections create a successor, preserve signed evidence and revoke unsigned predecessor invitations. This is an issued record register, not statutory certification or a signed PDF generator.
- Invitations use two random UUIDs (244 random bits), store only SHA-256 token hashes, expire in 1–168 hours, and support revocation. Customer acceptance checks the exact document digest, fixed explicit consent and a name. Workspace locks serialize issue, revocation and signing; a request can be signed once. Server timestamps and append-only, client-inaccessible events record issue, invitation, revocation and acceptance. Existing drafts/revisions are not rewritten.
- The optional panel in `team-sync-test.html` reuses the existing isolated staff sign-in/transport. It can issue a fully synced version, show audit history, create a link and revoke unsigned requests. It sends no email or messages. A connection failure after issue/invite requires checking history before retrying.
- `signature-test.html` is a separate loopback-only customer acceptance screen. It uses the existing isolated configuration format, rejects the original production endpoint, needs no customer account, removes tokens from the URL fragment immediately, sends them only in POST bodies, keeps them in memory, verifies the canonical document SHA-256 before rendering, and renders values as text. No service-worker caching, analytics or browser-storage persistence. Configuration must be selected explicitly for this test UI. It is not a hosted customer-facing release.
- `Planner` exports calendar events with stable record UIDs, revisions, and 30/7-day display alarms. A calendar application handles alarms after import while this app is closed. UTF-8 line folding and text escaping prevent malformed events. Cancelled/completed visits are excluded. Calendar applications differ: re-import after edits, check alert settings, and manually remove obsolete imported events. This does not send unattended email/SMS or guarantee notification delivery.
- Driving-route links group active visits by engineer/date and preserve appointment order across postcode districts. The Maps handoff requires 2–10 stops with postcodes; no addresses leave the app until the link is opened. Google then receives addresses and supplies directions/traffic. This does not optimise appointments or calculate travel time locally. Existing district grouping and job packs remain.
- Four beginner Academy lessons cover electrical safety, intruder alarm awareness, emergency lighting and systematic diagnosis. Each includes six questions, feedback/retry and a supervised fictional exercise. Ten lessons are available. Intermediate/advanced and manufacturer-specific practical content still require verified source material and competent review.
